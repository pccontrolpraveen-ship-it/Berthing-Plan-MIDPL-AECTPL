# Security Policy

## Repository visibility

This repository is **private** internal operational software. It documents
berth dimensions, crane positions, bollard allocations and operating rules
for MIDPL Kattupalli. Do not fork it to a personal public account, paste
its contents into public forums or AI tools outside approved channels, or
enable GitHub Pages unless a publicly reachable demo URL has been cleared.

## Reporting a vulnerability

Report suspected security problems privately to the product owner
(Tushar — GM & Terminal Head, MIDPL Kattupalli) or the APSEZ IT security
team. Do not open a public issue. Include what you observed, how to
reproduce it, and the impact you expect.

## What must never be committed

| Never commit | Why |
|---|---|
| `.env` files, connection strings, API keys, JWT secrets | Direct compromise of the production system |
| Real staff mobile numbers in test data | Personal data |
| Vessel schedules, manifests, line or agent correspondence | Commercially confidential |
| Database dumps or report exports containing live operational data | Commercially confidential |

The repository `.gitignore` blocks the common cases, but the rule is the
author's responsibility, not the tool's.

If a secret is committed, treat it as compromised: rotate the credential
first, then remove it from the repository and its history.

## Authentication

Delivered in 2.10; see `docs/AUTH.md` for how to run it. Two modes, and the
login screen states which one is in force.

**Server mode** — a PortVision server is reachable. The one-time code is
generated by a CSPRNG on the server, stored only as a scrypt hash, expires in
five minutes, is single-use, is capped at five wrong attempts and five requests
per number per quarter hour, and is never returned in an HTTP response. **The
role is read from the `users` table**, so it is a fact about the account rather
than a claim by the browser. Access tokens are short-lived JWTs; refresh tokens
are opaque, stored hashed, and rotated on every use. Every endpoint except
`/api/health` requires a valid token, and writes additionally require Vessel
Planner or Admin. Sign-ins, failures and refusals are recorded in `auth_events`.

`PORTVISION_JWT_SECRET` (32+ characters) is mandatory and the server refuses to
start without it. There is deliberately no built-in default: a shipped default
signing key is worse than no authentication, because every deployment would
share it while appearing secure.

**Standalone** — no server is reachable. There is nothing to authenticate
against, so this is a local demo on one device: the role picker remains and the
code is the demo literal. It is labelled as a demo on the login screen rather
than presented as a login. Do not use standalone mode to hold real operational
data you rely on.

Accounts are created by an administrator (`server/manage-users.js`); there is no
self-registration, because who may edit a berthing plan is a decision for the
terminal.

### Known limitations

- **Tokens live in browser storage**, so a cross-site scripting flaw would
  expose them. The app renders through `innerHTML`, which is why values that
  came from a person are escaped on the way out; that mitigation is the reason
  the storage choice is acceptable, not an excuse to stop caring about it.
- **OTP delivery is pluggable and unconfigured by default.** `log` prints the
  code to the server log — development only. Set
  `PORTVISION_OTP_TRANSPORT=webhook` and point it at an SMS gateway before any
  real deployment; `none` refuses to deliver rather than pretending to.
- **`PORTVISION_ALLOWED_ORIGINS` is unset by default**, which keeps CORS open
  for development. Set it in production.

## Remaining production requirements

Tracked as NFR-06 and FR-106/FR-107 in `docs/SRS.md`:

- HTTPS everywhere; no plain HTTP endpoint (also required for the mobile builds
  — see `docs/MOBILE.md`)
- A real OTP transport configured, not the development logger
- `PORTVISION_ALLOWED_ORIGINS` restricted to the deployed front ends
- Audit logging extended to every create, update and delete of plan data, not
  only authentication events
- Daily automated database backups with tested restore
- Dependency vulnerability scanning enabled on the repository

## Safety note

PORTVISION 3D is a planning aid. Berthing, mooring and cargo decisions
remain subject to the judgement of the terminal's marine and operations
personnel, the Master's authority, pilotage advice and applicable port
regulations. A validation message in this software is never a substitute
for a safety assessment on the quay.
